# OCR and speech-to-text run as follow-on accessioning workflows

Text derivatives are generated by their own workflows: OCR text for images and PDFs (`ocrWF`) and transcripts and captions for audio and video (`speechToTextWF`). The depositor UI sets `runOCR` or `runSpeechToText` in the workflow context. At the end of accessioning, `end-accession` starts the matching workflow for the *next* version. That workflow opens the version, sends the files to an external engine, adds the results to the object, and closes the version, which runs accessionWF again to shelve and preserve the new files. This keeps slow, optional processing off the main accessioning path and reuses the existing versioning and preservation machinery.

| Workflow | Engine | Transport |
| --- | --- | --- |
| ocrWF | ABBYY FineReader server | CIFS hot folder `/abbyy`, watched by `abbyy_watcher` |
| speechToTextWF | Whisper on AWS Batch (sul-dlss/speech-to-text) | An S3 bucket per environment, AWS Batch, and an SQS "done" queue watched by `speech_to_text_watcher` |

## Considered options

- **Trigger from the `end-accession.completed` RabbitMQ message** instead of from the end-accession robot. EDA 0022 considered this. Not built.
- **Generate derivatives inside accessionWF.** Rejected: these derivatives are not required for delivery (unlike JP2s), and they are slow.

## Consequences

- Each derivative run creates another object version. OCR and speech-to-text are mutually exclusive for a single run.
- Speech-to-text is intentionally off in prod for now. common-accessioning-prod has no AWS Batch queue configured, and Argo gates the option behind `features.speech_to_text_workflow`.
- The external engines are outside SDR VMs. The ABBYY server is reached over a CIFS share, and Whisper runs on AWS Batch.
- `captionWF.xml` is an orphaned template with no robots. speechToTextWF replaced it.
